# 00 LT Slide Style Extraction

複数の過去資料を比較し、発表者固有の表現を `config/slide-style-profile.md` に保存する。このスキルは個別のLTを作らない。抽出したルールを、01 Story、02 Blueprint、04 Build、05 Reviewで再利用できる形にする。

## Required Reads

- 出力を作る前に `references/style-profile-schema.md` を読む。
- 資料を分類・判断するときは `references/extraction-criteria.md` を読む。
- 出力後に `scripts/validate_style_profile.py config/slide-style-profile.md` を実行する。

## Inputs

次の一つ以上を扱う。Speaker Deck URL、PDF、HTMLスライド、Markdown原稿、発表台本、過去の `01-story.yaml`、過去の `02-blueprint.yaml`。

- URLは取得可能な範囲で本文と視覚表現を確認する。視覚を取得できない場合は、視覚ルールを推測しない。
- 複数資料では、各資料にだけ現れる特徴と共通特徴を分ける。
- 原則3資料以上を分析する。2資料以下の場合はドラフトとして保存し、恒常ルールを `MUST` にしない。
- 既存プロファイルがある場合は無条件に置換しない。根拠数、資料の新しさ、矛盾を比較し、強まったルールだけを更新する。

## Workflow

1. 入力資料を一覧化し、作成時期、テーマ、取得できたテキスト・視覚情報、利用上の制約を記録する。
2. 各資料について、発表者の立ち位置、ストーリー展開、見出し、記号、感情の転換、失敗と成功、技術的具体物、レイアウトを観察する。
3. 同一テーマ由来の特徴と、資料をまたいで再現される特徴を分離する。3件以上を強い特徴、2件を候補、1件を資料固有として扱う。
4. 特徴を語句の寄せ集めにせず、`role`、`applies_when`、`guidance`、`next_slide`、`limits`、`evidence` を持つ再利用パターンへ変換する。
5. `references/style-profile-schema.md` の順序で `config/slide-style-profile.md` を作成または更新する。各ルールに `MUST`、`SHOULD`、`MAY`、`MUST NOT` のいずれかの強度を付ける。
6. 実際に存在しない失敗・感情・実験を足さない。可読性、技術的正確性、発表時間をスタイルより優先する。
7. 検証スクリプトを実行する。エラーがあれば、見出し、ルールの発生条件・上限、根拠資料を補ってから完了する。

## Extraction Rules

- 過去資料の文章を大量にコピーしない。再利用できる文型と適用場面へ抽象化する。
- 感嘆符、三点リーダー、顔文字、短いstatementは、使う場面と頻度上限をセットで記録する。
- 成功だけでなく失敗や途中結果が学びに寄与する場合は、その見せ方と次に示す原因・再試行を記録する。
- 口調だけで技術情報を曖昧にしない。入力、出力、数値、制約、ファイル名、エラー、成果物などの具体性を別ルールとして残す。
- 誤字、レイアウト崩れ、技術的に不正確な説明、テーマ固有の流行語を個性として保存しない。
- すべてのページへ個性を適用しない。特に `MUST NOT` と Application Limits を使い、模倣的な連続表現を防ぐ。

## Integration Contract

01、02、04、05はプロファイルがあるときだけ参照する。

- 01は発表者の姿勢、ストーリー、失敗・成功、具体性、話者ノートのルールを使う。スタイルを理由に事実を作らない。
- 02は見出し、感情の転換、視覚構成、適用上限を設計図へ反映する。
- 04は02の設計図だけを忠実に実装する。プロファイルから新しい表現を追加しない。
- 05は反映不足・過剰適用・根拠のない体験の生成をレビューする。

## Quality Gate

- 3件以上の根拠資料、または2件以下のドラフトであることが明記されている。
- 各再利用パターンに発生条件、具体的な指針、上限、根拠がある。
- 視覚情報を取得できなかった領域を推測していない。
- 共通特徴と資料固有の特徴を区別している。
- 過剰な記号・感情表現・模倣を防ぐ `MUST NOT` がある。
- `scripts/validate_style_profile.py` が成功する。
